# 交互体验改进需求：响应、回执、进度与恢复

日期：2026-11-20。状态：P0 与 P1 的约定范围已有代码；下面的勾选只在真机和云端持久化通过后勾上，当前都未勾选。

配套文档：[技术方案](interaction-experience-design.md) · [现有产品目标](../tasks/prd-personal-super-agent.md) · [当前实现契约](implementation-contract.md) · [实施状态](implementation-status.md)。

## 1. 背景与问题

用户反馈当前交互“不智能、慢、卡”，并确认以下三类问题都存在：

1. 发消息或交办后，长时间不知道是否收到、是否开始。
2. 执行过程没有清楚的进展，失败后不知道原因。
3. 连接、审批、停止、切换等操作缺少明确反馈。

本轮目标是建立可理解、可追踪、可恢复的交互闭环，同时减少串行刷新和调度造成的等待。覆盖 Mac SwiftUI、Android React Native、云端控制服务和本机执行节点。

## 2. 目标与原则

- 用户始终能分辨：指令是否保存、谁在处理、当前进展、阻塞原因、是否需要自己操作。
- 发送、暂停、回答等操作各自反馈，不因全页刷新锁住整个工作台。
- 等待有事实依据；没有新进展时保留最后已知事实、时间和连接状态。
- 查询和控制能够及时响应，不排在长模型回合之后。
- 断网、重启、重复点击、跨端并发后，消息、任务和动作保持一致。
- 清楚的交办按既有授权直接执行；只有目标歧义、业务决策或范围扩大时澄清。

“请求已收到”“执行电脑已接受”“实际已停止”“交付已验收”分别表达不同事实，不互相替代。消息处理结束也不表示其关联任务已经完成。

## 3. 核心交互

### 3.1 发消息与交办

点击发送后，原地出现带稳定身份的消息和“发送中”。服务端保存后改成“已收到”；真实接手后才显示“正在处理”。等待时说明可确认的原因，例如“主助理电脑离线，消息已保存”“主助理正在处理上一条消息”。无法取得原因时显示“尚未确认处理状态”，提供检查入口。

发送失败保留正文与任务关联。响应丢失时先按原身份查询或重传同一请求，不生成第二条交办。用户主动发起新的业务尝试与网络重传需要明确区分。

### 3.2 执行中

在当前对话中呈现关联任务的持续工作记录：当前阶段、最近完成的事实、最近进展时间、明确的等待原因及下一步动作。关键变化更新同一记录，详细步骤按需展开，避免每个工具事件都生成一条聊天消息。

示例：“已读取 3 个来源，正在对比价格变化；最近进展：12 秒前”。只在有实际计数时显示 3/5；不生成无依据的完成百分比、预计结束时间或模型内部推理。

### 3.3 查询、暂停与恢复

“进度呢”先返回任务快照与更新时间。明确针对单个任务的暂停、取消进入确定性控制路径；多个可能目标时先展示选择项。不能因主助理模型正在忙而禁止用户使用显式控制按钮。

暂停先显示“请求已收到”，设备接受后显示“正在暂停”，实际停止后显示“已暂停”。不能确认在途操作结果时显示“结果待核对”，保留证据入口。切换电脑或引擎必须沿用既有停止、检查点、租约和新 Run 规则。

### 3.4 错误与连接

错误就近说明发生在哪一步、哪些工作已保存、是否需要处理，以及可执行的恢复入口。写入成功但刷新失败时，应显示“已保存，状态同步失败”，保留当前内容。连接状态与任务状态分别显示：重连不等于任务失败，旧快照也不代表任务已停止。

## 5. 用户故事与验收标准

以下验收均针对待实现功能，未勾选项不代表已经通过。涉及界面的故事须在真实 Mac 客户端和 Android 模拟器或真机验证；HTML 设计稿或浏览器截图不能代替原生验收。各组件执行适用的类型检查、构建和必要行为测试。

### US-01：发送后立即看见消息（FR-01、05）

作为用户，我希望点击发送后立刻看见自己的消息，从而确认操作已经触发。

- [ ] 不等待消息 POST 或整页刷新便显示“发送中”。
- [ ] POST 成功后直接合并返回消息，后台刷新不阻塞输入与其他任务。
- [ ] 正文、记忆范围和任务归属在失败重试、导航切换中保留。
- [ ] 待发送消息及幂等身份在发送前持久保存，App 崩溃或重启后可恢复；恢复先核对已保存结果，再按原身份重传。

### US-02：重试不会重复派活（FR-01、07）

作为用户，我希望网络故障后可以安全重试同一请求。

- [ ] POST 已提交但响应丢失时，沿用原身份恢复，只出现一条消息和一份业务交办。
- [ ] 同身份不同正文或授权范围返回冲突，不静默覆盖。
- [ ] 网络重传与真实执行的新尝试有不同交互语义。

### US-03：知道消息在等谁（FR-02、03）

作为用户，我希望知道消息已保存、正在等待还是已经接手。

- [ ] 助理电脑离线与前一条消息处理中显示可核实的不同原因。
- [ ] 接手状态由实际接手事实产生，不根据最后一条消息角色推断。
- [ ] 助理崩溃后的未知处理显示需核对，不自动重复模型调用。

### US-04：在对话中看见真实进展（FR-03）

作为用户，我希望不用切到多个页面就能知道任务最近完成了什么。

- [ ] 派发、设备接受、运行、等待输入、交付等变化可回到原交办上下文。
- [ ] 进展有来源与时间；无结构化业务计数时不显示虚构比例。
- [ ] 没有新事件时不循环生成“正在分析”等假进展；需要时显示检查状态入口。

### US-05：暂停请求有完整回执（FR-04、07）

作为用户，我希望分清暂停请求已收到和任务实际已暂停。

- [ ] 接受请求后可用同一 action_id 追踪设备接受与实际结果。
- [ ] 在途动作未静止前，不显示“已暂停”或启动替代执行。
- [ ] 超时、离线及结果不确定分别解释；响应重传不重复触发动作。

### US-06：询问进度不等长模型回合（FR-04）

作为用户，我希望在助理忙时仍能及时查询和控制明确的任务。

- [ ] 状态查询读取权威快照，注明更新时间，不触发新模型调用。
- [ ] 当前任务明确的快捷指令和显式按钮走同一权限及版本校验路径。
- [ ] 存在多个候选或只是讨论、引用指令时，不直接控制猜测的任务。

### US-07：一个任务忙时仍能做别的事（FR-05）

作为用户，我希望当前任务执行或刷新时仍能输入、派新任务和回答其他问题。

- [ ] 忙碌只禁用确实冲突的动作，不锁住全局工作台。
- [ ] 同资源互斥动作保留服务端冲突校验，不能靠按钮防重代替。
- [ ] 并发返回不会清空另一个任务的草稿或覆盖更新后的状态。

### US-08：断网后知道状态是否新鲜（FR-06、08）

作为用户，我希望断网时保留最后状态，联网后自动对齐。

- [ ] 页面显示正在重连、最后同步时间及必要的陈旧提示。
- [ ] 正常 SSE 连接轮换不造成持续错误提示；持续失败才升级连接问题。
- [ ] 事件已收到但关联 REST 失败时仍能重试；重启后不因游标已前移漏掉待同步对象。
- [ ] 游标、待发送消息和缓存按“服务端地址＋登录用户”隔离；账号、服务器及测试/生产环境切换不会串用。

### US-09：错误告诉我下一步（FR-07）

作为用户，我希望失败后知道已完成哪些工作以及如何恢复。

- [ ] 已保存但刷新失败的提示不会被外层成功路径清除。
- [ ] 可恢复错误提供重连、刷新、查看电脑、回答、核对或重试等对应入口。
- [ ] 结果未知时先核对；不诱导重新提交可能已生效的业务动作。

### US-10：跨端处理与结束状态一致（FR-08、09）

作为用户，我希望在另一端处理问题后，两端都显示同一个有效结果。

- [ ] 双端同时回答或审批只产生一个有效结果，冲突端刷新并解释。
- [ ] Run 完成后仍可显示待验收，独立验收通过才宣布目标完成。
- [ ] 问题、失败和交付记录可回到对应任务；过时提醒被抑制。
- [ ] 厂商接受通知不显示为设备已展示或用户已读。

## 6. 性能目标与测量

下列为建议验收目标，不是现有性能结论。先记录基线，再在同一环境比较；统计普通可用网络与可用服务下的 p95，弱网、离线、排队另列，不能删除失败样本美化指标。

| 指标 | 初始目标 | 测量边界 |
| --- | --- | --- |
| 本地发送反馈 | ≤100 ms | 点击到“发送中”绘制，同一客户端单调时钟 |
| 服务端保存回执 | ≤1 s | 客户端发请求到持久化回执呈现，排除后续模型和全量刷新 |
| 状态查询、显式控制的接受回执 | ≤1 s | 请求到快照或请求接受反馈；不代表设备已停止 |
| 已到达客户端的事件呈现 | ≤1 s | 接收事件到相应视图更新；补拉失败独立统计 |
| 前台恢复后的快照对齐 | ≤5 s | 连接可用后到可见任务和待处理事项对齐；注明样本数据规模 |

首次测量每端至少 30 次普通交互，记录构建版本、设备、网络、数据规模、样本数、失败数和 p50/p95。补充离线电脑、长模型、慢截图、断网恢复、服务重启和双端并发场景。

记录发送、保存、接手、模型开始/结束、派发、设备接受、首条真实进展、结果、验收及客户端同步等节点。跨设备时间不能直接相减作为精确时延；使用各端单调耗时和受控的请求链路关联。

## 7. 范围与约束

- 沿用云端 PostgreSQL 控制服务、本机模型/浏览器/凭据和节点 SQLite 执行日志的架构。
- 保留现有租约、epoch、幂等、版本、预算、权限、独立验收与未知结果核对规则。
- 本轮不承诺新模型、更换供应商、真实模型首字时间、自动接任、完整远程桌面或操作系统通知实际送达。
- 不为显示进度而上传模型内部推理、工具原始参数/结果、认证文件、密钥、Cookie 或完整数据库连接串。
- 此文档不授权生产操作；实现与云端部署按现有项目流程执行。

## 8. 实施优先级与退出条件

第一批 P0：发送本地反馈与局部忙碌、服务端收件/处理状态、基础任务生命周期、显式动作回执、连接与补齐、错误保留、基础耗时测量。必要时先解除控制和续租对截图等无关慢请求的串行依赖。Mac 与 Android 都覆盖，不能只优化一个客户端。控制回执的 ≤1 s 目标仅指云端接受，不保证实际停止时间；实际停止必须有节点事实支持。

第二批 P1：细化真实过程进度、聊天查询/控制快捷路径、上下文选择、节点独立循环与反馈延迟优化。优先验证慢模型和慢截图不会挡住查询及控制。

每批提交应附需求编号、变更范围、必要自动化结果、原生验证记录、测量条件和未验证项。云集成测试仅在显式专用 TEST_DATABASE_URL 配置时运行；缺失时明确跳过，不使用生产库或本机数据库替代。真实后台通知仍按[通知方案](notification-delivery.md)单独验收。

## 9. 待测量与可调项

- 模型处理、节点轮询、云接口与客户端刷新分别占用多少等待时间。
- 不同运行时能提供哪些真实阶段事件；没有能力的运行时应展示哪些有限事实。
- 持续静默多久提示检查、步骤聚合频率及重连提示宽限期；初始值见技术方案，按实测调整。
- 原生后台/休眠恢复、弱网和 Android 系统策略下的实际表现。

上述待测项不阻塞先实现可靠回执与错误反馈；任何能力或性能目标在完成对应验收前都保持“待验证”。
