# 交互体验改进技术方案

日期：2026-11-20。状态：约定范围已实现在代码中；迁移 004 尚未应用到云端，真机与云 TEST 尚未验收。

本文落实[交互体验需求](interaction-experience-requirements.md)。接口和事件已进入代码与[实现集成契约](implementation-contract.md)。性能目标仍是待测口径，不是已达到的结果。第 1 节表格是实施前的代码事实。
当前生效接口以[实现集成契约](implementation-contract.md)及共享类型为准；[协议设计](protocol-v1.md)中的长期规划也不能直接当作可调用接口。

## 1. 设计判断与现状证据

需要同时解决三个问题：实际链路等待过长、已发生的状态没有及时展示、操作失败后缺少明确恢复入口。单纯缩短轮询或增加“思考中”动画不能覆盖这些问题。

| 已核查事实 | 对体验的影响 | 本方案处理 |
| --- | --- | --- |
| [节点默认配置](../apps/node/src/config.ts)的 `poll_interval_ms` 为 2000；[节点 tick](../apps/node/src/agent.ts)顺序等待心跳、回报、记忆增量、命令、续租、画面，之后启动助手 | 前置慢请求会推迟后续工作；实际延迟占比仍需测量 | 独立循环、超时与分段计时 |
| [planMessage](../apps/node/src/agent.ts)等待 `adapter.execute` 返回，规划阶段的 `emit` 只保存 usage；`running` journal 位于本机 | 模型长回合期间，客户端缺少可靠的处理阶段回执 | 服务端消息处理状态与阶段事件 |
| [assistant](../apps/node/src/agent.ts)使用 `assistantBusy`，一次读取收件箱第一条并等待规划结束 | 后发的查询或控制聊天可能排队 | 保留规划顺序，分离查询与控制 |
| [Service.action](../apps/control-server/src/service.ts)返回 `{action_id,status:'accepted'}`，活动运行先进入 stopping/pausing；action ID 当前只是响应中的随机值 | 请求接受与真正停止之间缺少可查询操作记录 | 持久操作回执 |
| [dispatchTenant](../apps/control-server/src/service.ts)创建 dispatched 运行时发出 `run.started`，摘要仍是等待电脑接受 | 事件名称不能直接作为“模型已开始”的依据 | 按真实运行状态投影，新增明确阶段 |
| [Mac WorkspaceModel](../apps/macos/Sources/SuperAgentMac/WorkspaceModel.swift)发送后调用包含多个串行请求的 refresh；[Android App](../apps/android/src/App.tsx)也有提交后 reload 的流程 | 发送完成的体感可能受无关数据刷新影响 | 本地消息先展示，返回结果局部合并 |

这里没有通过生产日志或真机复现确认哪一项耗时最多。实施后的本机计时见[实施状态](implementation-status.md)，仍不能代替真机 p95。

## 2. 边界与不变量

1. 云端 PostgreSQL 保存跨设备消息、处理回执、操作回执、任务状态和持久事件；Node SQLite 保存本机执行日志、待上报事件和恢复证据。
2. 模型、账号、凭据、浏览器控制和执行仍位于用户 Mac；服务端状态查询不能变成云端模型调用。
3. 消息已接收、消息已处理、任务已启动、运行结束、交付通过分别表达不同事实。
4. 超时只说明等待超过阈值，不能据此声称请求失败、模型未调用或业务操作未发生。
5. 重试传输保持同一业务身份；重做模型或业务执行需要显式的新尝试和已有预算授权流程。
6. 新循环不能绕过租约 epoch、scope、预算、工具互斥、人工接管和未知结果核对。

## 3. 客户端提交与局部状态

### 3.1 一次用户操作只分配一次身份

用户按发送时，先生成稳定 `client_message_id` 和 `Idempotency-Key`，在请求发出前把正文、目标任务、执行偏好及记忆范围作为同一不可变提交持久保存到本地待发送队列。
请求超时、断网恢复和用户点击“重新发送”均重用原身份与内容；修改正文或授权范围后另建新提交，不能用旧 key 替换请求。
账号、服务地址、租户和本地操作 ID 共同隔离队列；客户端缓存、游标和 outbox 均至少按服务端地址与登录用户隔离。退出后停止重传，切换账号不得发送前一账号的内容。
App 崩溃、重启或导航切换后恢复原提交及身份，先核对服务端已有结果，再决定是否按原身份补传；不能重建一个随机身份自动发送。
本地存储使用客户端现有安全存储能力，按应用沙盒保护，不把待发送正文写入诊断日志。

客户端立即插入消息气泡，依次表达：`本地待发送 → 发送中 → 服务端已收到`。
收到现有 POST `/messages` 的返回值后，按 `client_message_id` 合并为服务端 Message，立即解除该提交的发送状态，无需等待全局 refresh。
SSE 先于 HTTP 返回时也用同一身份合并，避免出现两条相同消息。
HTTP 超时显示“发送结果待确认”，通过同一请求重传或身份查询对账；不能直接显示“未发送成功”。

### 3.2 操作范围内的 busy

以 `message:<localId>`、`task:<id>:control`、`review:<id>` 等键管理 pending，替代用一个全局 busy 阻塞工作台。
同一任务的冲突操作串行，重复点击复用正在进行的操作；其他任务、历史浏览和输入框仍可用。
发送中的消息保留可见内容；未提交草稿与已提交消息分开，失败时提供“编辑为新消息”和“继续确认原提交”两种明确操作。
待发送消息只有在确认未向服务端提交时才能直接本地删除；提交结果未知时，移除本地气泡不能被描述成撤回服务端执行。

## 4. 服务端消息处理回执

### 4.1 数据模型提案

新增消息处理记录，以 `(tenant_id, source_message_id)` 唯一关联源消息；消息正文仍保存在现有 messages 中。

| 字段 | 含义 |
| --- | --- |
| `id / source_message_id / version` | 回执身份、来源与单调递增版本 |
| `status` | `received / queued / processing / waiting_input / handled / failed / interrupted` |
| `phase` | 当前已证实阶段，如 `waiting_device / planning / preparing_tasks / replying` |
| `attempt_id / owner_device_id / owner_epoch` | 本次处理尝试和合法持有者 |
| `received_at / started_at / updated_at / completed_at` | 服务端记录的生命周期时间 |
| `last_progress_at / reason_code` | 最近有效进展与安全分类原因 |
| `plan_id / task_ids / reply_message_id` | 当前已持久化的关联对象 |
| `retry_mode` | `transport_only / explicit_new_attempt / reconcile_first / none` |

`handled` 表示这条输入已经产生持久回复、明确澄清或授权任务交接，不代表关联 Task 已完成。
需要用户回答时保存问题或澄清引用，状态为 waiting_input；新回答是新消息，关联原处理记录，不能改写原用户输入。
`failed` 用于已确认的处理失败；节点重启或模型调用结果不能证明时使用 interrupted，并保留未知用量及恢复说明。
存在有效持有者但无新进展时不自动标 failed，展示等待时长与“最近仍在线／连接未知”。

### 4.2 原子提交与恢复

POST `/messages` 在一个租户事务中提交 Message、初始 received 回执和 `message.created`，再返回现有 Message 响应。
节点认领处理记录后才上报 processing；认领和更新检查当前 assistant lease、设备和 epoch，终态不能被旧节点推进。
消息回复与 handled 的最终迁移在同一事务中完成，并写关联事件；任务交接失败不能把记录提前标为 handled。
持久计划、任务和最终回复继续使用稳定源消息身份去重，阶段记录不能成为另一条任务派发路径。
节点崩溃后先对账已有 plan、reply 和本地模型 journal；已提交结果恢复关联，没有结果的已发出模型调用转 interrupted，不自动再付费调用。
只有传输未确认的阶段/最终提交可以自动重传；显式新模型尝试继续使用现有活动根及 `#N` 预算规则。

### 4.3 新增接口提案

以下接口尚未实现；实施时必须同步协议类型、权限、响应 schema 和集成契约。

| 接口提案 | 用途与约束 |
| --- | --- |
| GET `/messages/:id/processing` | 登录用户读取本租户消息回执 |
| GET `/messages/by-client-id/:client_message_id` | 本人提交结果对账，返回 Message 及回执；不存在为404，不能把临时404直接解释为从未提交 |
| POST `/assistant/messages/:id/claim` | 有效 assistant lease 下原子认领，返回处理尝试；重复认领复用同一有效尝试 |
| POST `/assistant/messages/:id/progress` | 仅当前合法尝试更新阶段，带稳定 report ID、attempt ID 和预期版本 |
| GET `/workspace/snapshot` | 返回一致水位下的活跃对象摘要和事件 cursor，供首次进入与恢复使用 |

最终处理完成优先扩展现有 `/assistant/messages` 的事务，不新增一个可绕过回复/任务交接约束的任意“标完成”接口。
客户端显示的初始“服务端已收到”可以直接来自现有创建响应；新处理接口未就绪时不得显示“电脑已接收”。

## 5. 任务进度与完成

### 5.1 展示真实阶段

消息处理卡与任务执行卡独立关联，界面可连续呈现：服务端已收到 → 等待执行电脑 → 电脑已接收 → 正在理解目标 → 准备任务 → 执行中 → 交付核对 → 已完成。
这是一种展示路径，不强制所有请求经过所有阶段；纯聊天和状态查询可以直接结束消息处理。
Run 的 starting/running、ToolStep 的 started/completed、问题创建、交付提交和 Review 结果是阶段依据。
节点心跳只更新在线状态，不刷新 `last_progress_at`；模型未产生可展示进展时写“模型处理中，已等待…”，不能杜撰正在打开网页或编造完成百分比。
安全工具阶段使用现有白名单标题，不包含参数、网页正文、Cookie、认证 URL 或模型隐藏推理。
模型提供的摘要必须标记来源，不能替代工具回执或交付证据。

新增 `message.processing.changed`、`task.progress.changed` 等事件仅是提案；保留旧事件供兼容客户端使用。
现有 `run.started` 在过渡期继续发送，但新客户端依据 payload.state 区分 dispatched 和真正 running，不能把事件名翻译成“已执行”。
重复或晚到阶段根据 attempt、run、epoch 和实体 version 合并，旧运行不能覆盖当前运行进度。
连续进度可按短时间窗口合并；问题、失败、控制终态、交付与业务终态不能被节流丢弃。

### 5.2 完成和通知

Run succeeded 后仍沿用现有 awaiting_review 与独立验收规则；收到模型文本“完成”不能把 Task 改为 succeeded。
聊天回复先说明“执行已结束，正在核对”或“交付待你核对”，验收通过后再报告业务完成。
服务端持久状态是通知来源，相同交付/问题/失败去重；用户已处理或被新 Run 替换时抑制过时通知。
通知继续遵守[通知投递方案](notification-delivery.md)：provider 接受不等于设备显示，更不等于用户已读或问题已处理。
应用内最终结果与通知点击进入同一真实对象，不另外生成一条无法追踪的摘要任务。

## 6. 确定性查询与控制

### 6.1 P0：显式按钮回执

现有 POST `/tasks/:id/actions` 及返回 `{action_id,status:'accepted'}` 保持兼容；提案是在同一事务里持久化对应 action，而不是只返回随机 ID。
创建/动作仍要求稳定幂等键与 If-Match；同键同请求返回原 action，同键不同请求返回409。
新增 GET `/actions/:id` 和 `action.changed` 事件作为提案，记录 action、task、绑定 run/epoch、状态、时间及安全错误码。
操作状态为 `accepted / delivered / applying / completed / failed / result_unknown / superseded`；只对已发生的事实推进，未观察到的中间态可省略。
completed 是该操作的目标后置条件已证实：暂停/取消要求受管执行静止；切换要求旧运行静止、检查点及新运行交接条件满足。
resume/retry 的操作完成定义为合法新运行已开始，任务本身仍可继续执行；开始前被取消则原操作为 superseded。
超时或租约丢失不能直接标 completed；在途副作用不确定时进入 result_unknown 并提供核对入口。
重复停止已经终态的任务可返回 completed 的幂等 no-op 回执，并明确原因。

节点控制信封增加可选 action ID，旧节点缺少该字段时服务端依据确定的运行终态补齐操作结果，无法证明 delivered 时不伪造。
若旧运行结束、目标版本变化或新 Run 已替代，原 action 必须重新验证目标；不得让旧取消信号停止新 Run。
客户端依次显示“停止请求已收到／等待电脑处理／已停止”，请求回包不能立即显示“已停止”。

### 6.2 P1：聊天快通道与上下文

支持有限、可解释的确定性意图：查看当前进度、暂停、继续、取消，以及选择明确任务后的重试/切换。
优先使用明确任务 ID、当前任务详情绑定或用户已经确认的引用；整个账户只有一个符合指令的任务时也可绑定，并显示该任务名称。
存在多个候选、跨会话引用不明或语义包含条件时，先展示任务选择与操作摘要；不得用“最新任务”猜测取消目标。
快通道只匹配明确语法和授权动作；复杂条件、混合目标或不确定自然语言交给普通理解路径，不以低置信分类直接执行。
状态询问直接读取授权快照、最近阶段、等待原因和数据时间，不调用模型，也不排在 planner 后面。
控制动作复用同一 actions API 和授权校验，不新增降低 If-Match、预算或 scope 要求的捷径。
聊天产生的控制请求也保存源消息与 action 关联，使消息回执、按钮回执和任务状态能互相追踪。
客户端按 thread、明确任务选择和 source message 维护上下文；返回页面后恢复关联，不能仅靠最近20条文本猜测工作对象。

实施时核对到两条必须保留的旧行为，并已写进代码：已有待确认方案时，“确认 / 开始执行 / 确认执行 / 取消 / 拒绝 / 不要执行 / 取消执行”继续交给原规划，快通道不把它们当成任务取消。用户从多个任务里选定一项后，唯一匹配的“选择 <编号前缀>”只返回该任务的权威状态，不执行暂停或取消；多个前缀仍先选择。

## 7. Node 调度拆分

P0 让控制回执和基础消息阶段可以独立上报，并解除控制及续租对截图等无关慢请求的串行依赖；完整分循环在 P1 实施，不以增加 planner 并发代替修复阻塞。

| 循环 | 职责 | 并发约束 |
| --- | --- | --- |
| 控制与命令 | 拉取动作、命令、更新本地取消门闩 | 独立 single-flight，取消优先于开始新执行 |
| 租约与心跳 | 设备、Run、assistant 和预算存活 | 各身份独立续租，超时保留现有 fail-closed 行为 |
| 持久回报 | SQLite outbox 向服务端补传 | single-flight，稳定 envelope/producer seq，不等待截图 |
| 助手收件箱 | 消息认领、规划与持久交接 | 同一对话的目标变更保持顺序，默认单规划器 |
| 记忆同步 | 消费记忆失效事件 | single-flight，鉴权失败不回放旧正文 |
| 画面 | 按需采集和上传最新帧 | 有界队列只保留新帧，不能阻塞控制与续租 |

每个循环设置独立超时、退避和退出信号，避免 setInterval 重入叠加请求；用“当前工作完成后安排下一次”或等价调度实现。
共享执行对象由单一状态所有者或逐 Run 的串行队列更新，网络等待不得持有全局锁。
停止首先关闭新工具入口，再处理在途操作、停止受管子树、保存回执和检查点，最后宣告静止。
租约 epoch 丢失立即禁止新工具/模型调用，重连不能自动复活过期授权；人工接管和浏览器槽位仍由既有互斥机制保护。
模型使用自己的运行取消信号；后发用户控制不能等待同一模型回合结束才进入停止逻辑。
共享根 lockfile 与协议变更由协调者统一合并；各组件分配明确文件归属，禁止竞争安装依赖。

## 8. SSE、投影与恢复

保留现有 SSE 加 REST 对齐架构。新增状态、receipt 和对应事件在云端同一业务事务中提交。
区分收到的事件游标和已完成投影的持久游标；只有实体更新或可重放的失效标记已可靠保存后，才推进后者。
如果事件触发的详情 GET 失败，不能只推进游标后遗忘：保留该对象 dirty 标记并重试，或保留事件等待投影完成。
首版优先选择顺序投影后提交连续水位；后续若采用持久事件 inbox，必须原子保存事件、dirty 对象及游标，再异步更新视图。
事件按 `stream_seq` 和 event ID 去重，实体按 version 防止慢 REST 响应覆盖新状态；数值游标不能使用字符串字典序比较。
读到无法处理的新事件时保存可恢复失效标记并重新读取对应快照，不能静默丢失待回答问题或控制结果。
鉴权失效停止自动重连并提示登录；普通断网指数退避加抖动；账号切换清理连接，按用户和服务地址隔离 cursor。
初始重连提示宽限为5秒，正常约25秒连接轮换不直接展示报错；持续断连超过宽限才展示重连横幅。15秒无真实进展可出现检查入口，60秒无进展突出最近已知阶段和连接事实，均不自动判失败。以上阈值实施后按实测调整。

新增 snapshot 提案必须在一致事务水位下返回活跃消息回执、任务、操作、问题与 cursor；历史正文另行分页。
重新 bootstrap 时先保存快照，再补读该 cursor 之后的事件。不能把多个不同时间的 REST 列表拼成“无缝快照”。
若事件保留策略启用，游标过期按协议设计返回410并触发重新 bootstrap；现有服务未支持该错误前，客户端不能假定它已经存在。
应用回前台先展示已有数据及“正在同步”，同步失败保留内容并标最近成功时间，不清空为假空列表。
连接状态区分“与服务端连接”和“执行电脑在线”；SSE 连接成功不能证明 Worker 可用。

## 9. 错误与诊断

错误统一映射为用户可采取的下一步：传输待确认、登录过期、电脑离线、引擎不可用、版本冲突、预算限制、执行失败、结果未知。
同一操作就地展示错误与恢复入口；全局连接横幅只表示全局连接问题，不覆盖局部业务错误。
409/412 先对账对象和原 action，不把刷新失败解释为原操作失败；新版本再次提交必须经过目标核验。
诊断详情保留 request ID、client message ID、source message、processing attempt、plan、task、run、action 和事件水位的关联。
诊断只保存白名单时间、状态、阶段和分类码；不上传 Codex 认证文件、模型 Key、Cookie、设备私钥、完整数据库连接串、工具参数或用户正文。
用户可复制一份脱敏诊断摘要，区分模型等待、节点离线、服务端等待、事件传输和客户端投影延迟。

## 10. 分批实施、兼容与回滚

| 批次 | 内容 | 对应需求 |
| --- | --- | --- |
| P0-A | 客户端本地提交队列、稳定幂等、局部合并与 pending、错误恢复；基础时间点 | FR-01、05、07、10 |
| P0-B | 消息持久处理状态、基础生命周期、显式控制操作回执；解除控制及续租对无关慢任务的阻塞 | FR-02、03基础部分、04显式控制部分、09基础语义 |
| P0-C | SSE 投影重试、游标安全、断线/前后台对账及跨端基本一致 | FR-06、08 |
| P1-A | 真实细分进度、聊天状态/控制快通道、明确上下文关联 | FR-03、04聊天部分、08 |
| P1-B | Node 完整独立循环、延迟优化、通知与诊断分析完善；P0继续沿用已有完成及通知语义 | FR-05、09、10 |

服务端先增加可选字段和新查询能力，再更新 Node，最后更新客户端；新客户端通过明确能力标记启用新增协议，缺失标记走现有兼容路径。
旧客户端继续收到 Message 和 `{action_id,status:'accepted'}`；旧 Node 继续使用原消息与回报接口，服务端只推导有证据的阶段。
新表、索引和 RLS 使用追加迁移 `004_interaction_receipts.sql`，不回填历史处理时间，不修改已生效的 001/002/003。该文件已在仓库中，尚未应用到云端。五个 `INTERACTION_*` 标志缺省开启，所以新服务接流量前要先应用 004，或把标志设为 `0` / `false`。
历史消息不批量伪造处理时间；能证明已有回复/计划交接时标历史 handled，不能证明的显示“历史处理状态未知”，不重新入队调用模型。
功能开关分别控制处理状态展示、操作跟踪、快通道和分循环，便于逐项回退。
回滚保留新增数据和幂等身份，停止新行为而不删除回执；正在执行的 Run、未决动作和未知结果先对账，禁止回滚触发重复模型或业务操作。
迁移和部署由用户在云端执行；本方案不授权本地 Docker、数据库服务或服务端镜像构建。

## 11. 指标与验证

以下是初始验收目标，需按真实设备和网络基线校准；不作为当前已达到的性能声明。

| 指标 | 初始目标或验收口径 |
| --- | --- |
| 点击至本地气泡/操作反馈 | P95 ≤100ms，无需等待网络 |
| 服务端持久接收延迟 | 拆出客户端网络与服务端事务耗时，正常网络 P95 目标≤1s |
| 显式控制接受回执 | 普通网络下请求至云端接受反馈 P95 目标≤1s，不包含实际停止 |
| 已到客户端的事件呈现 | 接收事件至视图更新 P95 目标≤1s；补拉失败独立统计 |
| 前台恢复后的快照对齐 | 连接可用至任务和待处理事项对齐 P95 目标≤5s，注明数据规模 |
| 排队与模型等待 | 分别记录收到→认领、认领→模型首事件、模型结束→任务派发，不合并为一个“响应时间” |
| 停止操作 | 单独记录接受、节点收到、禁止新工具、执行静止；不得用接受延迟冒充停止耗时 |
| 反馈空窗 | 活跃工作始终可见当前阶段、经过时间及最近有效更新；超过阈值展示原因/连接不确定性 |
| 重复与恢复 | 同一提交仅一条消息/一个业务动作；断网、重启、回前台不丢未决问题与结果 |

服务端时间用于同服务内阶段差值，节点使用单调时钟计算本机耗时，客户端计算本地展示耗时；跨设备时钟偏差需单列，不能直接相减当精确延迟。每端初始至少30次普通交互，记录版本、设备、网络、数据规模、样本与失败数及p50/p95，弱网和离线另列。
验证覆盖发送响应丢失、HTTP/SSE先后倒置、同key不同body、重复点击、退出换账号、投影GET失败、旧版本回包、游标恢复和多任务歧义选择。
执行验证覆盖慢模型、慢记忆/截图上传、控制并发、租约过期、旧epoch回报、停止时在途副作用、重启不重放付费模型、旧Node兼容及回滚恢复。
消息处理终态与业务任务终态分别断言；验收未通过时不能产生“目标已完成”通知。
本地使用可控适配器测试状态和并发；涉及持久事务、去重、RLS和事件恢复的集成测试仅使用显式配置的云端 `TEST_DATABASE_URL`，未配置时明确跳过。
完成后仍须 Mac/Android 真机前后台、休眠、断网和实际 Worker 验收；替身模型或传输 mock 通过不能替代这些结果。

## 12. 实施对照（2026-11-20）

代码已覆盖第 10 节的 P0 与 P1。下面是核对后写进实现、并和初稿不同的约束。

- 级联取消只持久化用户点击的那一条父任务回执。子任务按 `cascade=false` 取消，不再各写一份回执。
- 绑定运行丢失或结果未知时，停止类回执进入 `result_unknown`，原因是 `reconcile_required`。租约超时本身不标 completed。
- 工作区快照除了未终态和待验收任务，也包括 `delivery_status=pending` 的任务，并带最近 50 条消息。这比“只返回未终态加待验收”略宽，避免待核对交付从首屏消失。
- 快通道开启后，若句子仍留在收件箱且服务端没有写下收件回执，节点每次轮询都直接返回，不调用模型，也不再本地执行同一句。能力接口失败不缓存，下一条消息会重新查询。
- 命令到期路径会推进操作回执，但仍不补发这条路径原先就缺少的 `task.changed`。保持原事件，避免云端事件快照突然多出一种旧路径没有的事件。
- 诊断只记录 `interaction_timing` 的名称、毫秒和 `ok`/`error`。进度摘要使用步骤标题加“已完成 / 未完成 / 结果未知 / 进行中”，或固定短语“交付待核对 / 交付已验收 / 交付未通过 / 交付还需要补充 / 等待你的回答”。不复制审阅正文、问题正文或工具参数。
